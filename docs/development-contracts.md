# Foundation development contracts

`src/server/db/index.ts` exports `db`, `pool`, the `Database` type, and each table. Schema ownership is centralized in `src/server/db/schema.ts`. Use Drizzle migrations under `db/migrations`; generate their metadata as part of the same change. Tables use UUID IDs and UTC timestamps. `organization` contains the single editable installation profile, constrained by `singleton_key=1`. Login `user` records remain separate from future network people.

`src/server/auth/auth.ts` exports lazy `getAuth()`. It configures Better Auth with its Drizzle adapter, database sessions, UUID IDs, database-backed rate limiting, and disabled registration. Do not expose new library endpoints without reviewing their access policy. The HTTP route only exposes signin, signout, get-session and current-password change.

`requireActor(headers)` returns `{ id, name, email, role }` after checking both a live library session and the active database user. `requireAdmin(headers)` additionally checks the current role. Every domain entry point for private records must call one of these; a layout check does not authorize a mutation. Page helpers may redirect unauthenticated users, but API handlers return an explicit 401/403.

`src/server/auth/service.ts` owns invitation/bootstrap/access transactions. Bootstrap and access changes share a PostgreSQL transaction advisory lock, and invitation acceptance locks its invitation row. Credential insertion uses Better Auth's exported password hash function and the adapter's credential schema. Admin service methods recheck the current actor inside their transaction.

`DomainError` contains a stable `code`, safe message, and HTTP `status`. `jsonRoute` maps these and Zod validation failures to safe JSON. Internal exceptions produce a generic response and minimal operational logging. `readJson` caps JSON input at 16 KiB before parsing. `checkOrigin` requires the configured app origin on custom mutation routes. Public setup/invitation endpoints use global per-installation database counters to bound attempts.

Use runtime validation for all new inputs. Domain logic belongs under `src/server` or future `src/modules`; client UI must not compute hidden scoring or trust submitted account roles. Protected pages use the `(workspace)` route group. Current UI routes are `/dashboard`, `/settings`, `/login`, `/setup`, and `/invite`.

All tests use fictional data. The integration helper refuses destructive reset unless both DB URLs match and use an isolated test name. Tests of future modules must avoid mutating another agent's database or development server. The foundation worker uses pi_t01 and port 3101; the feature integration database is pi_integration.

Node/runtime and package versions are pinned in `.nvmrc`, Dockerfile, package.json and package-lock.json. The current Drizzle Kit transitive esbuild override fixes a published dev-server advisory; migration generation and all project checks must still run when changing it.

## First deterministic workflow

Domain tables in `src/server/db/schema.ts` now include `need`, `person`, `affiliation`, `company`, `evidence`, `capability`, `relationship`, `opportunity`, `assessment`, `assessmentEvidence`, and `activity`. Each business record has an explicit organization FK, recorder, revision, and timestamps. Person IDs are separate from login user IDs. Affiliations permit several roles; an external contact role is not an internal introduction root. Professional relationship endpoints are a person and company; personal endpoints are two different people. Database checks enforce endpoint combinations, previous-employment state, date order, score bounds, and planned/completed event timestamps.

`src/modules/records/validation.ts` exports runtime record schemas and `RecordKind`. `saveRecord(headers, kind, input)` in its service performs authorized transactional create/edit operations; `getWorkspaceData(headers)` returns the permitted workspace projection. `workspaceContext` checks a live actor and saved organization, `assertReference` rejects foreign/nonexistent references, and `invalidateAssessments` advances input revisions and marks proposals for review. Invalid inputs make no writes. URLs are supplied source references, never fetched. Evidence stores the claim, URL or attribution, excerpt, observation/review dates, review state and recorder.

Record mutations and opportunity generation lock the organization row while applying changes or reading the generation snapshot. Factor review uses the same lock and a locked opportunity to serialize assessment versions. Invalidation currently applies conservatively to every opportunity in the installation. T-05 can narrow dependency tracking, add generation-run/idempotency contracts, review gates and broader lifecycle semantics while preserving immutable historical versions and manual fields.

`src/modules/network/paths.ts` exports `PathInput`, `isCurrent`, and `findDirectPaths`. The T-02 result contains one current direct organization/person/company path and one historical lead. Dates, explicit source IDs, evidence review state, reported strength, and dated willingness remain attached to edges. Ended, unknown, future and disputed/superseded records cannot form its current route. A shared employer does not create an acquaintance. Refusal remains visible and is respected; recorded yes does not establish relevance, present consent, or decision authority. T-04 extends this typed result with bounded personal intermediaries, ranking and a full historical/current view. It can own this module and `src/components/path-graph.tsx` without schema changes. Contact roles and access4 require explicit human review with supported evidence; a job title never establishes authority.

`src/modules/opportunities/contracts.ts` defines path, claim, generated brief, assessment, candidate, review, activity, and future AI context inputs. Path snapshots contain node IDs as well as names, and edges contain evidence IDs. T-08 must redact/remove private historical path/source material when deleting a person. Generated claims refer to supplied evidence and preserve supplied/reviewed/disputed/superseded states; inferences and questions are separate.

`scoring.ts` exports the exact versioned `rubric`, factor schemas, `unknownFactors`, and `calculatePriority`. Its eight 0–4/null factors return priority, known-factor coverage and unknowns without renormalization. Coverage is scoring coverage, not verified evidence completeness. The UI renders values, rationale, origin and source information; it does not compute its own priority. Deterministic category matching supports at most fit2, current recorded employment supports at most relationship2, and feasibility/authority/incentive remain unknown without further input. A human factor review requires rationale and evidence or an explicit organization assessment; it appends an assessment version.

`generateOpportunity`, `getOpportunityDetail`, `editOpportunity`, and `reviewFactors` live in the opportunity service. The initial generator evaluates one user-selected saved company/active need and returns a recorded brief without AI. The database prevents duplicate active company/need/type records. Regeneration appends a snapshot and preserves `manualBrief`, owner and activity. Every proposal remains `needs_review`; T-05 adds readiness decisions. Contact-role and value-exchange templates are expressly proposals, not known company incentives or invented managers.

`src/modules/outreach/service.ts` exports `activityInput`, `saveActivity`, `localCalendarDay`, and `getDueActions`. Planning requires an active login-account owner and a target person/role. Completing an action records a UTC timestamp; it cannot revert to a draft. Calendar follow-ups use the organization timezone and appear on the dashboard. This records actions and sends no messages. T-03/T-06 may add user-supplied historical occurrence dates and full pipeline transitions, with validated provenance and history rather than overwriting completed events.

Protected record pages are `/needs`, `/network`, `/companies`, `/opportunities`, and `/opportunities/[id]`. `RecordEditor` supplies manual create/edit forms; T-03 owns onboarding/import forms and any new partnership/import schema migration. T-04 owns graph/path code and independent graph UI. Coordinate shared schema, journal, record forms, navigation and opportunity detail changes explicitly. Do not regenerate overlapping migrations independently from stale bases.

## Onboarding, imports and recorded history

T-03 owns migration `0004_dear_hannibal_king` and its snapshot/journal entry. It adds `partnership`, `previousOutreach`, `onboarding` and `importBatch`, plus organization/source-ID uniqueness for people, companies, relationships and partnerships. Future migration generation must start after adopting this metadata. Domain keys remain UUID FKs. Company domains and person emails normalize to lowercase during validation; source IDs are case-sensitive stable identifiers.

`RecordKind`, `getWorkspaceData` and `RecordEditor` now include `partnerships` and `previousOutreach`. Partnership inputs expose companyId, title, type, state, startDate, endDate, description and optional evidenceId/sourceId. Previous outreach exposes companyId, optional personId or recorded contactRole, channel, occurredDate, description, outcome and source attribution. Its occurrence date must be a real calendar date no later than today. It is separate from planned/completed `activity`; imports or edits never complete a new outreach action.

The T-04 history adapter can project partnership as `{id,companyId,kind:'partnership',label:title,occurredDate:startDate,state,description}` and previous outreach as `{id,companyId,kind:'outreach',label:channel,occurredDate,state:outcome,description}`. These provide history context and never establish personal acquaintance, willingness or decision authority. T-06 may extend partnership agreement/outcomes through this existing table without creating duplicate writable graph edges.

`saveRecordInTransaction(tx, context, kind, input)` is an internal seam for atomic multi-record imports. Its caller must acquire an authenticated `workspaceContext` and lock the organization row. Public service entry points continue to obtain a live actor. Manual mutations and import commitments use the same organization lock as generation, then advance assessment input revisions conservatively. Import commitments also lock their batch, preflight every selected row against current identities/revisions/references, and store one idempotent result. T-05 should retain this common lock ordering.

`src/modules/imports/csv.ts` exports bounded `parseCsv`, explicit `mapRow`, template fields and record validators. Its service exports preview/get/cancel/commit and `purgeExpiredImports`. HTTP uploads cap the request stream at 5 MiB plus 64 KiB multipart overhead before `formData`, then cap the actual CSV at 5 MiB. Confirm JSON is separately bounded at 1 MiB for up to 5,000 decisions. No uploaded file is stored. Pending normalized rows are retained privately for one hour and cleared on the next import operation/page visit after expiry. There is no wall-clock cleanup daemon. Commit/cancel clear rows immediately; summary/mappings remain. T-08 should provide operator retention controls and clear private pending rows/mappings when deleting related data.

`src/modules/onboarding/service.ts` exports `steps`, `getOnboarding`, `saveOnboarding` and `readiness`. Progress is shared within the single installation, persists current step/skips/completion and removes a skipped marker when a step is revisited and continued. Readiness requires an active need, matching company capability and supplied/reviewed source observed no later than today. Personal paths are optional. The source remains a supplied claim until reviewed. Missing support leads to concrete record/evidence tasks. No cash-company shortcut or automatic verified fit is introduced.

New private screens are `/onboarding`, `/imports` and `/partnerships`, reachable from settings. Their components use a separate CSS module. Coordinator navigation wiring may link the fresh-dashboard profile call to onboarding and link the graph-review step to the focused `/graph` page after T-04 integration. T-03 deliberately leaves graph/path services, opportunity detail and the shared navigation layout unchanged.

## Candidate runs and readiness review

T-05 owns migration `0005_nervous_vanisher`, generated after adopting T-03's `0004` metadata. It adds `companyNeedIncentive`, `generationRun`, `opportunityReview`, a prior-closed-proposal link and `assessment.humanFactorKeys`. Explicit factor reviews mark the supplied keys; regeneration preserves those values and provenance while appending a new immutable assessment and requiring readiness again. Current source support excludes future observation/review dates, disputed and superseded records. Their claims remain visible with a question rather than becoming current support.

`src/modules/opportunities/runs.ts` exports `getCandidatePreviews`, `saveIncentive`, `startGenerationRun`, `listGenerationRuns` and `retryGenerationRun`. Runtime input selects one active need and up to 20 distinct saved companies. Omitted company IDs select supported capabilities or evidenced incentive mappings; cash has no match-all rule. Explicit selection can include unsupported candidates with gaps. Closed history requires acknowledgment; an ongoing discussion for another tuple requires a separate explicit acknowledgment. Same-tuple pursuing/agreed work is skipped unless `refreshOpportunityId` identifies that exact active proposal. A shared company does not prohibit deliberately reviewed support for a different need/type.

Runs persist requester, exact candidate selection, idempotency key/payload fingerprint, need revision, status, attempt, start/finish and safe error category. Assessment revisions and source/path snapshots carry finer input provenance. The organization row serializes writes and assessment numbering; active company/need/type uniqueness remains enforced by PostgreSQL. A run is synchronous and atomic, with a 20-second database statement bound. A committed `running` row can survive a process failure even if assessment writes roll back. Startup recovery runs explicitly before `npm run dev`, `npm run start` and the Compose server command, never inside a route or build import. It marks abandoned runs `interrupted`. One explicit retry is permitted; completed replays return the same result, and exhaustion requires a fresh deliberate request after resolving the cause. There is no queue, automatic retry, cross-process execution lease or durable-job claim. Operate one server per installation.

`src/modules/opportunities/review.ts` exports `reviewOpportunity` and `assertOpportunityReady(tx, lockedOpportunity)`. T-06 must invoke the latter within its lifecycle transaction before entering `pursuing`. Readiness binds the latest assessment ID, opportunity input revision and manual brief revision. Reviewed fit, a concrete ask, relevant role or supported named contact, permitted approach and first action are required. A recorded refusal blocks that introduction; an explicitly reviewed cold alternative can pass. A named warm target must be the selected route's terminal person: a shared employer does not prove access to another manager. Role-only introductions remain requests to verify suitable access. Edits and regeneration invalidate readiness. The saved action-plan panel shows the reviewed target and selected sourced route/cold mode separately from immutable assessment route snapshots; an invalidated plan is labelled historical.

T-07 should save AI suggestion drafts separately for human review. `writeAssessment` and `generateInTransaction` are internal transactional seams, not permission to replace human factors, manual briefs or source provenance. T-08 must include review target/path IDs, generation selections/results, prior-opportunity links, incentive evidence and all historical assessment snapshots in export/deletion/retention handling. No source URLs are fetched by these modules and no outreach is sent.

## Isolated fictional demo and UI disclosures

T-09 owns `0009_dark_zarek`, generated after adopting T-08's released `0008_late_pestilence` metadata. `demoInstallation` is a singleton persisted marker with dataset version, organization identity and `seeding`/`ready` state. Default `APPLICATION_MODE` is `live`. Only guarded CLI seed/reset may create the demo marker; there is no reset endpoint or public fake provider. The guard checks the same actual write pool, matching explicit demo URLs, restricted login/database identity, local runtime URL, empty seed or matching reset sentinel, fictional identity/accounts and absence of active non-operator database connections. Reset deletes the known fictional records atomically, then rebuilds through domain services. Interrupted rebuilds retain a recoverable marker. See `docs/demo.md` for operator commands and test companion provisioning.

The action plan remains separate from assessment snapshots. Current readiness shows the selected target, route/cold mode, ask and first action; a stale plan is historical, with the current proposed brief visible separately. Native disclosures reduce initial detail density while preserving keyboard access to source excerpts, snapshots, score factors, editors and versions. Graph canvases mount only with a visible measured container; the relational text remains available independently. `AiSettings` cancels initial-load effects and rejects late results after editing begins; it changes no AI service contract.
