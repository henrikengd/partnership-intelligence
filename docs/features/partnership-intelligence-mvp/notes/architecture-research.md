# Architecture feasibility research

Checked against official documentation on 2 October 2026. This note supports the saved MVP scope. The architecture and safeguards below are proposals, not agreed product decisions or verified application behavior.

## Verified technical facts

| Area | What the official documentation establishes | Implication for this MVP |
| --- | --- | --- |
| Full-stack hosting | Next.js supports deployment as a Node.js server or Docker container with its server features. Static export has limited feature support. | A single Next.js App Router application can host the UI and server operations without requiring Vercel. Use a server deployment for private database access and AI requests. [Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying) |
| Self-hosting | Next.js recommends a reverse proxy for internet-facing self-hosting. Server environment variables are private by default; `NEXT_PUBLIC_` values enter browser bundles. Multiple app instances add cache coordination and deployment considerations. | Keep the initial deployment to one application instance. Store database credentials and AI keys only on the server. Document HTTPS and reverse-proxy setup before a real deployment. [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting) |
| Authentication | Next.js recommends an authentication library. Server Actions and Route Handlers must check authorization as public API entry points. UI visibility and top-level layout checks do not secure all entry points. | A single-organization deployment still needs accounts, sessions, and server-side permission checks near data access and mutations. Leave the auth library choice for Prepare after confirming the login requirements. [Next.js authentication](https://nextjs.org/docs/app/guides/authentication) |
| Relationship traversal | PostgreSQL supports recursive common table expressions, graph traversal, path tracking, and cycle detection. | Ordinary relationship tables can support bounded introduction paths. A graph database is not technically required for this first version. Performance for the intended dataset still needs implementation tests. [PostgreSQL recursive queries](https://www.postgresql.org/docs/current/queries-with.html) |
| Data access | Drizzle provides PostgreSQL support through `node-postgres` and `postgres.js`. | Drizzle is a feasible TypeScript data layer. It does not remove the need for database constraints, input validation, authorization, or traversal limits. [Drizzle PostgreSQL support](https://orm.drizzle.team/docs/get-started-postgresql) |
| Graph UI | React Flow renders React-based nodes and edges. Its core library is MIT-licensed; Pro provides additional examples and support. | A relationship-path view can use the core library without purchasing Pro. Graph rendering is separate from database traversal and opportunity ranking. [React Flow quick start](https://reactflow.dev/learn), [React Flow licensing and Pro](https://reactflow.dev/pro) |
| Local and small deployment | Docker Compose supports single-host production deployment and isolated test environments. | An app service and PostgreSQL service are a credible starting point. Compose alone does not provide database backups or a managed operations service. [Docker Compose use cases](https://docs.docker.com/compose/intro/features-uses/) |
| Structured AI output | Official OpenAI documentation supports JSON Schema structured output, with a supported subset of schema features. It explicitly notes that outputs can contain mistakes and that applications must handle refusals and incomplete responses. | Structured output can enforce a brief's shape, but it cannot establish whether a claim or evidence reference is true. Validate returned entity and evidence IDs against the request's allowed records. [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) |
| Untrusted research input | OpenAI documents prompt injection and private-data leakage risks. It advises keeping untrusted input out of higher-priority developer instructions and constraining data flow. | Imported website text must remain evidence data. It must not gain authority to change instructions, access records, send messages, or write to the database. ## Proposed implementation boundaries

These recommendations follow from the product constraints. The documentation above establishes feasibility, not user agreement.

- Use one TypeScript application and one PostgreSQL database per deployed organization. A shared hosted multi-tenant service would need a separate scope and isolation review.
- Put graph traversal, candidate selection, scoring, and evidence checks in server-side domain modules. Use foreign keys and validated edge types. Traversal should reject invalid edge combinations, detect cycles, limit path depth, and cap the number of returned paths. More connections alone must not imply a usable introduction.
- Use React Flow for a filtered company or opportunity subgraph. Start with read-only inspection and a textual path equivalent. A complete graph editor or force-directed rendering of every person adds complexity without being required to inspect an opportunity.
- Start with manual company facts and cited source links. General web discovery and arbitrary URL fetching add provider, cost, prompt-injection, and request-security concerns. If fetching is later included, bound response sizes and time, block private network destinations, and recheck redirected destinations.
- Make the AI provider optional. A small provider interface can support an OpenAI adapter and a deterministic demo adapter. The demo adapter should use fake fixtures or explicit templates and identify simulated output. No API key should be necessary to explore the demo or record private data locally.
- Build AI context from one need, one company, selected approved facts, and the relevant introduction paths. Never send the entire private relationship graph to the model. Replace personal identities with record IDs where feasible and exclude contact details unless the task requires them and the deployment permits disclosure.
- Keep public company research separate from private relationship context. A research request does not need member names or employers. Limit any later model tools to the specific records and actions needed for the task; the first version needs no autonomous tools.
- Require structured outputs with references to supplied evidence IDs. Check schema validity, ID membership, and references before persistence. Display model claims as proposed inferences. A valid evidence ID does not prove that the cited fact supports the generated claim; retain evidence text and human review.
- Compute factor scores and total priority deterministically. AI may propose explanations or highlight missing facts, but it must not set success probabilities, silently strengthen relationship records, or turn inferred company capabilities into confirmed facts.
- Bound each generation request by candidate count, input size, output size, timeout, and retry count. Persist the run status and allow retry after a visible failure. A provider refusal or timeout must leave facts and existing opportunities intact. Add a worker only if actual request duration or deployment constraints make it necessary.
- Keep private exports, uploads, database volumes, logs, and backups outside tracked public source. Do not log full AI contexts. Public demo fixtures must contain only fabricated data. Private deployments need documented backup and restore procedures before real use.
