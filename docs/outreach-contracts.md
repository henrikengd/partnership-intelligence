# Outreach lifecycle contracts

Migration `0006_foamy_veda` is the T-06 schema handoff. Adopt its schema, snapshot and journal before generating T-07 migration 0007. It adds `opportunity.partnershipId`, `activity.occurredDate`, `activity.followUpResolvedAt`, `activity.followUpResolvedBy` and the append-only `opportunityEvent` table. Existing completion timestamps retain their recording-time meaning; legacy occurrence dates remain unknown rather than being invented.

Lifecycle events contain explicit organization/opportunity FKs, action, from/to state, reason, source attribution, occurrence date, optional resulting partnership/readiness review FKs, recorder, request UUID/hash and UTC recording timestamp. Organization/request uniqueness supports idempotent retries. Agreement events require an agreed state, a resulting partnership and attribution. Decline/archive events require a reason. One opportunity links one resulting partnership; several opportunities may legitimately link the same broader collaboration.

T-06 public services will live under `src/modules/outreach/`: `transitionOpportunity(headers,id,input)`, `getLifecycleDetail(headers,id)`, `getPipeline(headers)`, `getCompanyHistory(headers,companyId)` and `updateFollowUp(headers,activityId,input)`. Lifecycle requests carry `requestId`, `action` (transition/reopen/agreement), expected `fromState`, optional `toState`, reason and agreement source/date plus either an existing same-company partnership ID or validated partnership creation fields. These services check a live actor and lock organization, then opportunity, then any activity. Entering pursuing calls T-05's `assertOpportunityReady`; lifecycle-only changes preserve the manual brief revision used by that guard. Completed retrospective communications do not require a pursuing review.

Follow-up completion is an explicit separate control. Completing an outreach event does not resolve its future follow-up. Rescheduling reopens the follow-up marker. Archived/declined work remains readable and does not fabricate completion. Completed event facts cannot become planned drafts or be silently overwritten. Occurrence dates and recording timestamps stay distinct.

`LifecycleControls` is a standalone client component. Root owns composing it into opportunity detail alongside T-07's independent AI component; T-06 does not edit shared detail/settings/startup scripts. Pipeline and company/outcome history views are T-06-owned. Root owns shared dashboard and navigation mounts. T-07 should use separate draft/provider tables and services; no lifecycle action automatically sends a message or invokes AI.

T-08 must include event reasons/source attribution, review links, resulting partnership links, actual activity dates and follow-up resolver metadata in private-data handling. Typed FKs permit explicit deletion/redaction policies. Public source contains only fictional verification inputs.

## Integration mounts

`getLifecycleDetail(headers,id)` returns `{record,events,partnerships,today}` for `<LifecycleControls detail={detail}/>`; `today` uses the organization time zone. `<OutreachActivities opportunityId={id} people={data.people} activities={activities} today={detail.today}/>` includes actual completion recording and per-activity `<FollowUpControls activity={activity}/>` controls. Root may replace the old activity form with this component in opportunity detail. The independent `/pipeline/[id]` page already mounts all controls. Root should add a `/pipeline` navigation link; existing dashboard `getDueActions` automatically gains unresolved-only filtering and closed-work suppression.

The public pursue endpoint delegates to the lifecycle transaction, preserving readiness-review references in lifecycle history. Lifecycle changes retain the opportunity manual-brief revision; they do not make an outdated assessment current. Explicit reopening rejects another active company/need/type proposal. Archived agreed work restores its existing partnership link; it never creates a second outcome.

Agreement occurrence is when the agreement was reached, independently of the contribution's effective start/end period. Both new and existing same-company partnerships support agreement before contribution starts. Source and actual agreement date plus explicit confirmation are required. Request-ID retries are immutable; concurrent requests serialize on the organization/opportunity locks, and one opportunity keeps one resulting partnership. Partnership manual editing and CSV transaction saving reject company reassignment while either an opportunity or lifecycle event references that partnership. Unlinked corrections remain allowed.

Completed communications preserve factual kind/target/channel/description and known actual dates. Unknown legacy actual dates remain null on unrelated edits. Completing an action preserves its follow-up; explicit resolution of the same dated follow-up is idempotent. Changing a follow-up date clears its resolution regardless of a stale client marker. The form clears the checkbox on a date edit, remounts for refreshed server values and disables saving while refresh is pending. The network-history projection uses actual `occurredDate`, including null for legacy unknown dates, rather than UTC recording timestamps.

The company history service adds lifecycle events, current/past contributions, manual actions and prior imported outreach, keeping occurrence dates and recording timestamps distinct. These are recorded organization-level histories, never proof of a personal introduction path. No module in this workflow invokes an email provider or sends messages.
